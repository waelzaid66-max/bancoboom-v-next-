# §2 · The fix

**`app.ts`** — the global `clerkMiddleware` is wrapped. A configuration failure yields *no auth context* rather than a 500. **An anonymous request to a public route is not an error.**

**`authGuard.ts`** — all **five** `getAuth` callers guarded, verified by a script rather than by eye:
```
line  48 GUARDED   requireAuth        → 401
line  93 GUARDED   requireDealerRole  → 401
line 131 GUARDED   requireAdminRole   → 401
line 193 GUARDED   optionalAuth       → continue anonymous
line 254 GUARDED   requireDbUser      → safe fallback
```
*My first pass patched three of five. The other two were found by grepping every call site and asking which were inside a `try` — condition ⑰ applied to myself, and this time it held.*

**`health.ts`** — `clerk_config` joins the readiness checks.

# §3 · ⚠️ Correction #38 — my `A-6` order was too strong, and a test proved it

**I ordered:** *"`/api/readyz` must return 503 when the Clerk key is missing."* **I implemented it, and `health.test.ts` failed:**
```
FAIL src/health.test.ts > GET /api/readyz is 200 when Postgres is reachable
AssertionError: expected 503 to be 200
```

**The test was right and my order was wrong.** *A 503 tells an orchestrator to stop routing traffic to the pod — and I had just proved the public marketplace, search, feed, sitemap and robots all serve perfectly in that state.* **Taking a working public site out of rotation because sign-in is misconfigured is a worse outcome than the defect.**

**Corrected design:** `clerk_config: "down"` appears in `checks`, is logged loudly, and does **not** flip readiness.
```json
{"status":"ok","checks":{"database":"ok", …, "clerk_config":"down"}}
```
**The operator sees the named failure; the orchestrator keeps routing what still works.**

> **I wrote the order from the symptom — "readiness lied to me" — without asking what a 503 would actually cause. The suite asked for me.**

# §4 · ⚠️ And a second-order effect of yesterday's `P0-5` migration

**Two test files failed on a foreign-key violation:**
```
FAIL src/services/LeadService.test.ts
FAIL src/services/ListingService.journey.test.ts
Error: Failed query: delete from "users" where "users"."id" = $1
```

**Traced:**
```
lead_history.buyer_id  → users   NO ACTION
lead_history.seller_id → users   NO ACTION
```

**Before `P0-5`, deleting a listing cascaded its `lead_history` rows away, so the user was then deletable. After `P0-5` those rows survive detached — and their `NO ACTION` reference blocks the delete.**

## The severity, measured rather than assumed
```
$ grep -rn "db.delete(users)" artifacts/api-server/src  --exclude tests
  (none)
```
**Production never hard-deletes a user.** Account deletion is a soft delete — `users.deletedAt`, checked throughout. **So this is a test-fixture ordering problem, not a product regression**, and the fix belongs in the fixture:
```ts
// lead_history survives its listing by design (Gate 4). Production never
// hard-deletes a user, so this ordering belongs to the fixture, not the schema.
await db.delete(leadHistory).where(or(eq(leadHistory.sellerId, id), eq(leadHistory.buyerId, id)));
await db.delete(users).where(eq(users.id, id));
```
**I did not widen the schema to make a test pass.** *`seller_id NOT NULL` is a correct constraint — a lead without a seller is meaningless.*
